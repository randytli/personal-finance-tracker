# M3 local runtime and recovery

M3 adds a local four-container runtime and manual recovery commands. `jobs` is a backup-command container only. It does not schedule syncs or backups; that is M4. No command in this document authorizes Production cutover.

## Isolated setup

1. Copy `.env.runtime.example`, `.env.runtime.db.example`, and `.env.runtime.backup.example` to matching `.local` files. Use a new isolated database name and a new random password in all three. Keep Plaid Sandbox credentials only in `.env.runtime.local`. Set `PFT_ALLOWED_ORIGIN` to the exact web origin if changing the port. Keep these files private and out of Git.
2. Create a private backup directory on the encrypted Windows host, outside Docker/WSL storage. Set `PFT_BACKUP_HOST_DIR` to its absolute WSL path, for example `/mnt/c/Users/tianr/PFTBackups/M3-Isolated`. Check its Windows ACL; only then set `PFT_BACKUP_HOST_ACL_VERIFIED=true` in the backup environment file if WSL reports permissive mode bits. Do not use `/tmp` for actual backups.
3. Set `PFT_APP_COMMIT` to the Git commit used to build the images. For example, `export PFT_APP_COMMIT=$(git rev-parse HEAD)`. Do not put credentials in this variable.
4. Build and start the isolated database: `docker compose -f compose.runtime.yml -p pft-m3-isolated build` then `docker compose -f compose.runtime.yml -p pft-m3-isolated up -d db`. Use the one-time explicit migration command `docker compose -f compose.runtime.yml -p pft-m3-isolated run --rm api python -m api.migrate_once`. The ordinary startup path is `docker compose -f compose.runtime.yml -p pft-m3-isolated up -d`. Subsequent starts use the ordinary path and do not rebuild or migrate.
5. Check `docker compose -f compose.runtime.yml -p pft-m3-isolated ps`, `http://127.0.0.1:3000/`, and a browser request to `/api/pft/analytics/monthly`. API and database have no published ports. `web` proxies `/api/pft/*` to `http://api:8000`; browser requests remain same origin. Database readiness gates API/jobs, and API health gates web. A failed schema or wrong Production database identity stops API startup before any migration.

The original `docker-compose.yml` and its `production-pilot` and `production-backfill` profiles are unchanged. The isolated project name creates its own `pft-m3-isolated_pgdata` volume. Never use `docker compose down -v` with financial data.

## Manual backup and recovery

With the isolated stack running, create a backup using `docker compose -f compose.runtime.yml -p pft-m3-isolated exec -T jobs python -m api.backup create --kind daily`. Use `weekly`, `monthly`, or `extra` for corresponding checkpoints. Backups are PostgreSQL 16 custom-format dumps in the host directory. The command writes a private temporary file, validates the archive listing, records a backup-consistent schema checksum plus application commit, file size, and SHA-256 in a JSON manifest, then publishes the archive. Retention after a successful new backup keeps 7 daily, 4 weekly, and 3 monthly manifests and dumps; `extra` checkpoints are not automatically pruned. A failed or interrupted dump leaves prior backups and retention untouched. Check the command's exit status; M3 has no automatic retry or status UI.

For an encrypted external copy, use the host Python environment: `python -m api.backup_crypto encrypt /path/to/pft-weekly-....dump /path/to/pft-weekly-....pftenc`. Create this bundle in the protected host directory, then copy it to external media. The password is entered twice without echo and must be stored independently in a password manager and recovery medium. The `PFTENC2` bundle contains both the dump and its JSON manifest, so recovery after whole-machine loss needs only the `.pftenc` file and independently recovered password. Store its reported SHA-256 separately and verify the copied file's SHA-256. Test password recovery with `python -m api.backup_crypto decrypt COPY.pftenc /private/path/recovered.dump`; decryption authenticates the bundle, validates the recovered dump against its embedded checksum and size, and creates both `recovered.dump` and `recovered.json` for the restore command. Existing outputs are never overwritten. The format uses scrypt-derived AES-256-GCM with a random salt and nonce; its header is authenticated, and the dump itself is not encrypted outside the bundle. Keep `PLAID_TOKEN_ENCRYPTION_KEY` independently recoverable as described in M0; the archive password does not replace that key.

Restore only into a **new** isolated database named `pft_restore_*`: `docker compose -f compose.runtime.yml -p pft-m3-isolated exec -T jobs python -m api.backup restore /backups/FILE.dump pft_restore_example`. The command checks the manifest and archive, rejects the source database, creates a new target, and runs `pg_restore --exit-on-error --no-owner --no-privileges`. It never uses `--clean`. A failed restore leaves its new target for inspection; create a different new target on retry. Database roles are not in `pg_dump`; create required roles before restoring when recovering to a new PostgreSQL cluster. Do not start jobs or allow Plaid access against the restored target. Compare Items, accounts, raw/normalized counts, removed rows, statement provenance, overrides, cursors, date ranges, and monthly analytics with a backup-consistent baseline. Independently test token-key recovery without printing token plaintext. The M0 report gives the baseline comparison method.

## Production cutover boundary (M6; separate approval required)

The M0-verified source is database `pft_production_backfill` in old container `personal-finance-tracker-db-production-backfill-1`, volume `personal-finance-tracker_pgdata_production_backfill` mounted at `/var/lib/postgresql/data`. `docker-compose.production.yml` names that exact volume as **external** and requires an existing PostgreSQL 16 data directory and control file before starting PostgreSQL. It cannot initialize an accidentally recreated empty volume. Its preflight also refuses missing old-container mount evidence, an unexpected mount destination, or a running volume user. This override has not been used to start Production in M3.

Before a proposed M6 cutover, obtain a fresh Production backup and preservation baseline, verify the volume identity with `python scripts/pft_volume_preflight.py`, and review the exact new runtime environment and rollback command. The preflight refuses while any running container mounts that volume. The old API and database writers must be stopped before running it; the new stack must never mount the volume concurrently with the old PostgreSQL container. A later approved cutover would use `docker compose -f compose.runtime.yml -f docker-compose.production.yml -p pft-runtime ...`, with the new runtime `DATABASE_URL` targeting `db:5432/pft_production_backfill` and `EXPECTED_DATABASE_NAME=pft_production_backfill`. Production migration, startup, validation, and rollback are M6 actions requiring explicit authorization and a scoped preservation check. M3 does not execute them.

## M3 validation — 2026-09-22

- All three images built and the four-service stack started under project `pft-m3-isolated`. The database mounted only `pft-m3-isolated_pgdata`; web alone published Windows loopback port 3100. API and web became healthy after the explicit migration. The Windows site and proxied analytics both returned HTTP 200.
- A container backup produced a PostgreSQL 16 custom dump with a SHA-256 manifest, schema fingerprint, and application commit. Restore into the new `pft_restore_m3_compose` database succeeded; source and restore each had 15 public tables. This test used a disposable `/tmp` bind mount, not the future protected Windows host backup directory.
- After a database restart, the proxied analytics route returned 200. With the isolated database stopped and API restarted, API readiness did not pass; after the database returned, analytics returned 200, web/API/database were healthy, and jobs was running. A wrong expected database name was rejected, and a write request without an allowed Origin returned 403.
- Final acceptance review: 213 Python tests passed with every PostgreSQL opt-in enabled, including `PFT_M3_SYNTHETIC_TEST=1`, and no skips. The populated recovery test preserved fingerprints for every table, including Items, accounts, raw/normalized rows, removals, statement evidence, cursors, and all four manual override tables. After deleting the original dump and manifest, the encrypted bundle alone recovered both files and restored successfully. Read-only restored monthly analytics matched the source ($20.00 net), synthetic token decryption passed, and the source fingerprint remained unchanged. No real token or Production data was used.
- Frontend: 21 Jest tests passed; the Next.js production build passed during initial M3 validation and its internal proxy configuration was rechecked in the built image. The corrected API/jobs images rebuilt successfully and imported the M2 statement-overlap dependency without network access. Rebuilt-stack readiness, analytics routing, backup, and restore passed. Image and Compose checks confirmed credential separation, no Docker socket mount, and exclusion of env files and statement CSV exports. Candidate files contained no configured secret values or private keys.
- Concrete review defects fixed: omitted statement-import code in backend images; external bundles missing their restore manifest; incomplete schema verification; missing Origin configuration allowing unprotected writes; backup pruning before durable manifest publication; and Production checks accepting absent old mount evidence or an empty external volume. The Production override resolves the exact M0 volume as external, its empty-volume guard failed closed on a disposable container, and its read-only preflight refused reuse while the old database was running. `git diff --check` and Python compilation passed.
- Docker Desktop startup also resumed the existing database containers under their preexisting restart policies. M3 made no Production database queries or application writes and made no Plaid calls. The isolated test containers were stopped after validation; their volume and test backup remain available for inspection.

The protected Windows host backup path, weekly encrypted media copy, and live Production volume reuse remain for an approved later cutover. Daily automated backup timing belongs to M4; no scheduler was added in M3.
