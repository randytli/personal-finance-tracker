### Headroom and $0 envelope

Retain the initial **50% / 70% / 20% targets unchanged**. At a verified D=300 s: normal p95 ≤150 s, worst plausible completion ≤210 s, reserve ≥60 s. Local baseline and grown samples fall below these numerical thresholds, but the **serverless gate remains UNKNOWN**. A shorter pg_net/HTTP path changes D and all targets: default 2 s is a blocker; frontend rewrite D≤120 s would mean 60/84/30 s and is excluded from scheduled execution. The existing 300 s application budget cannot reserve 60 s on a 300 s provider. A candidate ≤240 s application deadline needs evidence that setup, publication and bounded failure cleanup fit; do not change runtime defaults in this pass.

No claim that 0.2-second SDK delay bounds bank tail latency. Serial row-level SQL dominates growth. **Measured local sensitivity:** injecting 1 ms sleep per SQL statement on a grown no-op cycle produced 127.388 s total across 71,379 queries, versus ~40.486 s baseline median. Sleep granularity and blocking instrumentation add overhead; this is not measured cloud latency. Identity/connection read 0.0065 s, transaction context exits (including commit/savepoint/rollback plumbing) totaled 0.0132 s, maximum 0.0038 s; engine disposal 0.0052 s, zero checked-out connections after completion. This single sensitivity observation passes the 150 s normal target only arithmetically for D=300; at D=120 it exceeds the provider path itself. Real round trips, concurrent event-loop behavior and tails remain UNKNOWN. Test rather than assuming region co-location fixes it. Optimization would be separately reviewed only if evidence warrants it, preserving financial semantics.

Five-minute scheduling projects 8,640 ticks per 30 days. At local idle median 0.0089 s, even charging 2 GB for that duration gives ~0.043 GB-hours/month; an assumed **one-second** deployed idle duration instead gives 4.8 GB-hours. Thirty grown 43-second cycles add ~0.72 GB-hours at 2 GB. Cold/warm setup, backups, BFF/API requests, concurrency and allocation accounting must be added from provider measurements. At ~35 s CPU per daily grown cycle, 30 cycles project ~0.29 CPU hours, excluding all other usage.

One device viewing eight hours/day produces 19,200 status polls/month at 45 s; two devices 38,400. Financial refresh batches also read markers and page endpoints; real route fanout, BFF duplication, focus/manual calls, payload size and all existing account usage are unmeasured. Do not call 8,640 < 1 million an adequate budget proof. Supabase SQL egress includes retained-history reads; SDK payload size is not a substitute. No defensible calendar retention horizon from one generic dataset. Require managed DB/index/bloat/log-growth and egress measurements, early warning below quotas and a reviewed safe-stop/recovery procedure; do not prune financial history or send anti-pause traffic.

### Latency sensitivity curve (follow-up, 2026-10-01)

**This is a local injected-latency sensitivity test, not evidence of actual Vercel-to-Supabase performance.** A blocking sleep before each SQL statement approximates serial round trips on the local PG16 cluster; it excludes TLS, Supavisor, provider CPU contention, cold start, event-loop concurrency and bank latency. Raw results: [latency-curve.json](evidence/m5-2026-10-01/latency-curve.json); harness [pft_m5_latency_probe.py](../scripts/pft_m5_latency_probe.py) (delay cap raised to 5 ms; no other change).

Workload: retained grown synthetic schema, 35,619 raw + 35,619 normalized rows (~13.6× current), one no-op fetched `sync_all` per delay, 71,379 SQL statements. Measured sleep overshoot ≈0.1 ms. One sample per delay; no distribution or p95.

| Injected delay / query | Result | Run duration | Classification |
| --- | --- | ---: | ---: |
| 0 ms (cold cache after cluster restart) | success | 49.4 s | 20.8 s |
| 3 ms (effective 3.36 ms) | success | 287.3 s | 140.5 s |
| 4 ms | `TimeoutError` at existing `MAX_RUN_SECONDS=300` | 297.7 s | not run |
| 5 ms | `TimeoutError` at existing `MAX_RUN_SECONDS=300` | 298.1 s | not run |

Both timed-out runs recorded `failed` / `publication_failed`; cursors and row counts were unchanged, no advisory lock remained, no run was left `running` and no connection remained checked out. This is local cleanup evidence only.

**1. Current workload has substantial modeled headroom.** Linear model from the 0 ms baseline: ≈1.39 ms local work + ≈2.0 statements × round trip per retained row. At ~2,610 retained rows a no-op cycle models to ~9 s (1 ms), ~19 s (3 ms) or ~30 s (5 ms), against the 150 s normal target at D=300 s.

**2. Query amplification is approximately linear with retained history and remains an architectural risk.** Every cycle, including no-op, re-normalizes retained Item history and reclassifies full active scope (≈2.0 statements per retained row at 2,610 and at 35,619 rows). Wall time scales with retained rows × round trip, not with new activity.

**3. Growth horizon (corrected).** At the stated rough rate of **~1,300 retained rows/year** (2,610 rows over the ~730-day backfill; not a measured Production growth rate), years until a modeled no-op cycle reaches the 150 s normal target:

| Round trip | Modeled ms / retained row | Rows at 150 s | Years from ~2,610 rows |
| ---: | ---: | ---: | ---: |
| 1 ms | 3.4 | ~44,200 | ~32 |
| 2 ms | 5.4 | ~27,800 | ~19 |
| 3 ms | 7.4 (8.1 at measured effective 3.36 ms) | ~20,300 (~18,500) | ~13.6 (~12.2) |
| 4 ms | 9.4 | ~15,900 | ~10 |
| 5 ms | 11.4 | ~13,100 | ~8 |

Horizons inherit every limitation above, assume linearity and constant growth, and cover only normal no-op cycles: catch-up, retry and partial-failure cases are bounded by the separate 0.70 × D target and add fetched-page work.

**4. A 300 s application sync budget is not acceptable when the platform hard limit is also 300 s.** It leaves no reserve for cold start, setup, failure finalization and unlock; locally, timed-out finalization completed only ~2 s before the budget. Under a 300 s provider kill this could land before finalization, deferring recovery to the next tick's interrupted-run reconciliation, which has not been demonstrated on the provider.

**5. Deadline: no change yet.** `MAX_RUN_SECONDS` remains 300 for the existing Windows runtime. A lower bounded application deadline (for example ~240 s, preserving ≥max(30 s, 0.20 × D) reserve at D=300 s) is a **candidate only**; it must be validated against actual cloud cancellation, hard termination, finalization and unlock behavior before adoption.

**6. No query-amplification optimization yet.** Any reduction in per-row SQL would be a separately reviewed change preserving publication atomicity and financial semantics, considered only if real cloud measurements require it.

**Next decisive measurement:** actual Vercel-to-Supabase database round-trip latency and total `sync_all` wall time (current-size and grown synthetic history, cold and warm) on the disposable synthetic cloud environment.
